## 一餐分兩段：先打菜，再做勤務

每一餐的流程是**先「打菜流程」**（打飯打菜的當下，全員都有位置），**打完才做「勤務」**（洗碗、廚餘那些）。兩段是分開排的，同一個人早餐可能是「打菜 → 洗碗」，中餐是「包餐盒 → 廚餘、撤收」。班表與文字班表都照這個順序分成〔打菜〕與〔勤務〕兩區。

### 打菜流程

- **打飯**（固定2人）、**計數**（固定2人）、**抬飲料＋包餐盒**（固定2人）：在名冊上指定，每餐都是同一批人，不參與輪替。抬飲料的兩位抬完之後也一起包餐盒。
- **早餐不打飯**，所以早餐沒有「打飯」這一行，固定打飯的兩位那一餐改成一起**包餐盒**。（不把他們丟進打菜／蓋便當的輪替，是因為他們一天只有早餐才會進池子，次數永遠追不上別人，公平圖會把他們誤判成「明顯偏少」。）
- **打菜**：每道菜2人，所以「一飯5菜」＝打飯2 ＋ 打菜10。
- **蓋便當**：2人。
- **包餐盒**：扣掉上面所有角色之後，**剩下的人全部包餐盒**。
- 打菜與蓋便當在「沒有固定角色」的人之間依累計次數少者優先輪替，所以不會固定同幾個人打菜。
- **人不夠時的讓步順序**：① 先取消蓋便當，那2人改去打菜；② 還是不夠的話，最後幾道菜改成1人負責，並在班表上跳提醒。
- 菜量在「勤務設定 → 每餐菜量」逐日逐餐設定，也可以設每餐預設值（目前早2、中5、晚5）。中晚餐最多五道菜：五菜＝打飯2＋打菜10＋蓋便當2＋計數2＋抬飲料2＝18人，人剛好夠；六菜要20人就會不夠，蓋便當會被取消。

### 打完菜之後的勤務

- **洗碗**：全部人排成**一條隊伍照號碼輪**，順序是 **263 → 261 → 招員 → 旅部連**，接到底就繞回開頭。隊伍不含固定送便當的兩位（他們那一餐在外面跑便當）。人數看對照表（23 人時每餐 7 位）。進度記「下一個從誰開始」而不是「第幾個位置」，有人退伍時才不會跳過還沒輪到的人。

  （早期人少的時候是「兩梯輪流當起始梯、各自維護指標」的複雜做法，那是為了讓「一天洗兩次」的人也能公平輪替。人變多之後不需要了，改成最單純的單一佇列。）
- **換水**：早餐**撤收完**才做，一次 5 人，261／263／旅部連照號碼輪，**招員不排**（名冊可勾）。而且**不會跟當天早上撤收的人重複**。
- **廚餘／擦桌子／清地板收垃圾**：排除當餐洗碗與固定送便當人員後，依「該項勤務累計次數少者優先，同次數依 261→263、序號」分配。
- **抬便當上車／抬便當上樓**：**除了固定送便當的兩位以外，在場的人全部一起（洗碗的人也要）**。兩者人選相同，班表上合併成一行，而且因為就是「送便當以外全上」，直接寫規則不列名字。個人分工則顯示成「抬上車/上樓」。
- **抬洗衣籃上來（下午）／抬洗衣籃下去（睡前）**：各2人，依名冊順序兩人一組往下輪（送便當的兩位也要輪；名冊勾「免排洗衣籃」的人不輪）。今天睡前抬下去的那組，下一個排班日負責抬上來，所以不需要另外排。輪替從 2026/08/02 開始，第一天只有抬下去。進度是記「上一組最後一位是誰」而不是名冊位置，這樣有人退伍時才不會跳過還沒輪到的人。
- **送便當**：固定2人（預設261的7、8號）。此人退伍時會跳出提醒，需在名冊手動指定新人選。
- **撤收**：每餐固定 **早5／中7／晚7**，**這項勤務做最少次的人優先**，同次數照名冊號碼。**不是**每個人每天都要輪到一次（23 人、19 個名額，每天會有幾個人沒排到，靠累計次數輪流）。限制有四條：**固定送便當的兩位早、中在外面跑便當，撤收只排得到晚上**、**那一餐洗碗的人那一餐不排**、名冊勾「免排晚上撤收」的人不能排晚餐、採買的人早中不在。公平性靠「每個人在各餐別的撤收次數」平衡，次數少的優先被排到那一餐，不會有人固定只做早餐或只做晚餐。

  這四條會互相牽制，所以撤收不是用「排序後依序挑」，而是用**最小成本最大流**：貪心法會卡死（先被挑走的人可能剛好佔掉另一個人「唯一還能排的那一餐」），流量演算法則保證只要存在可行分法就一定找得到，而且在所有可行分法裡挑最公平的那個。圖只有二十幾個節點，速度不是問題。

  **人真的塞不下時**：如果晚餐能排的人太少（洗碗的人＋勾了免排晚上撤收的人），演算法會把人往中餐擠、盡量保住「早餐最輕鬆」，並在班表上寫清楚是哪一條限制造成的。極端情況下有人整天三餐都在洗碗或不在，那天就不排撤收給他，也會列出來。

  **名額沒坐滿不一定是錯**：每人一天最多排一次，當名額總數逼近當天人數時（例如 8/3 是 18 人 18 個名額），限制一交錯就湊不出完美配對，這是數學上的必然，稽核會列成「提醒」而不是錯誤。
- **採買**：週一～週四固定各一位（預設 週一呂胤玄、週二林柏翰、週三陳柏翰、週四陳俊穎），集合時間預設 週一三 0600、週二四 0450，另有「採買到哪一天為止」（預設 2026/08/04，之後就不排採買了），都可在「採買」分頁改。**採買的人當天早餐、中餐完全不排（打菜與勤務都不排，含撤收），晚餐才歸隊**，那兩餐的名額會自動少一位，人數才對得起來。集合時間會印在文字班表上。如果那天輪到的人已經退伍，產生班表時會跳提醒。
- **勤務人數**：依「**那一餐實際出勤人數**」查「勤務設定」的對照表，不是用整天人數。所以採買的人被抽掉、或退伍當天晚上少人時，各項名額會自動跟著調整，不用另外加減。每一列的數字加上固定 2 位送便當應該剛好等於出勤人數（例如 20 人：洗碗7＋廚餘6＋擦桌子2＋清地板3＋送便當2）。人數變少時的縮減順序是 **擦桌子 → 廚餘 → 清地板 → 洗碗 → 廚餘**。人數超過表格最大值時會套用最大那一列，多出來的人就當幫手。

  對不起來的時候不會有人完全沒事——大家都要抬便當——但會有人那一餐只抬便當、沒有別的勤務，班表上會直接提醒你去補那一列。

  **對照表是按「扣掉送便當之後還有幾個人」查的，不是按出勤人數。** 因為送便當是固定角色，人數由那兩位還在不在決定，不是可以自由分配的欄位；用出勤人數查會出事——8/6 早餐 19 人（送便當 2 位都在，其餘 17 人要分）跟 8/13 晚餐 19 人（只剩柏宇，其餘 18 人要分）需求差 1，同一列蓋不住。

- **設定改版會自動換新**：勤務人數對照表與預設菜量存在瀏覽器裡，而讀檔是「存的蓋過預設值」，所以程式改了預設值不會自動生效。這兩份東西有各自的版本號，程式裡的預設值一改就 +1，舊資料（含從雲端還原的）會自動換上新的。你自己逐日調過的菜量不會被動到。
- **加入／離開**：名冊可填每個人的加入日期與離開日期（都能預先填未來日期）。離開方式分兩種：
  - **退伍**：當天早餐、中餐照排，晚上才離營，所以那天晚上的勤務、撤收、洗衣籃都不排給他，文字班表顯示「已離營」。
  - **退出**（退出打飯班、調離）：當天早上起完全不排。

  加入日期之前的日子也不會排到他。
- **個別免排**：名冊每個人可以勾「免排洗衣籃」與「免排晚上撤收」。8/4 報到的五位新人預設兩個都勾起來。

  ⚠️ **「免排晚上撤收」勾越多人，代價越大**：晚餐能排撤收的人 ＝ 出勤 − 晚餐洗碗 − 勾了免排的人。五位新人都勾的情況下，晚餐常常只剩 2～4 個名額，人只好往早餐和中餐擠，14 天裡有 3 天沒辦法維持「早餐最輕鬆」。把這五個勾勾拿掉就能全部維持。要調的話在「名冊」分頁直接取消勾選即可。

## 先預覽、按確定才會記錄

「產生班表」分成兩步，避免測試時不小心污染公平次數：

1. **🔍 預覽**：只是計算給你看，不會寫入任何次數或狀態，可以重複按著玩。
2. **✅ 確定紀錄**：把結果真正存起來，這時才會累計洗碗/廚餘/…等次數、推進洗碗與撤收的輪值指標。

如果想全部歸零重來，到「名冊」頁面按「🔄 重置所有勤務紀錄」，次數、班表、輪值指標都會清空（人員名單與採買星期表保留）。

## 鎖定已公布的班表

「邊改規則邊公布勤務」會遇到一個問題：改完規則回頭看，那天的班表跟當初貼到群組的不一樣，大家就會覺得又改了。

所以「產生班表」頁面有 **🔒 鎖定這天**：把當初公布的那份「依餐別」文字班表整段貼回去（標號、分隔線都不用清），這天就永遠照那份走：

- 之後改勤務人數、菜量、名冊，**都不會動到已鎖定的日子**
- 次數照樣計入公平性總覽，跟大家實際做的一致
- 洗衣籃進度會接上鎖定的內容（今天鎖定誰抬下去，明天就是那組抬上來）
- LINE 機器人回的也是鎖定的版本
- 鎖定的日子在班表上會標示，隨時可以「解除鎖定」改回自動排班

如果鎖定的班表裡有人名冊上寫那天不在營（例如退伍日期填錯），班表照鎖定的版本顯示，但會提醒你去把名冊改對。

## 同一天永遠排出同一份班表

班表不是一天一天累加出來的，而是從「已確定的日期清單」配上名冊與各項設定**重播**推導出來的：每次有任何變動（包括改採買星期表、改退伍日期），系統都會依日期順序把所有已確定的日子重算一遍。因此

- 同一天不管重排幾次，只要名單與勤務設定沒變，結果一定一模一樣；
- 「重排這天」會自動清掉那天原本的結果再重算，不會殘留舊資料，也不會重複累計次數；
- 「預覽」看到的內容跟之後「確定紀錄」的結果保證一致；
- 可以「取消這天的紀錄」，之後再排回來還是同一份班表。

**公平性次數不會疊加**：次數不是每排一次就 +1，而是每次變動時把所有已確定的日子從零重數一遍。所以同一天重排幾次、取消再排回來、甚至倒著排，次數都完全一樣。`npm run verify:counts` 會完全不看系統存的次數、直接從每天的班表重數一遍再比對，並把上面幾種情境都跑過。

## 公平性總覽怎麼看

每項勤務一個圓形圖，**每個人固定佔一格**（角度都一樣，依名冊順序排），格子**往外伸得越長＝做越多次**（面積正比於次數）。淺色底代表那一格還是空的，也就是這個人還沒輪到。

之所以不用「照比例切派」，是因為次數 0 的人在比例派裡角度是 0、根本畫不出來——勤務還沒輪完一圈時（例如第一天擦桌子只有3人次），圖上就只會出現3塊，看不到其他人。改成等角度之後，該輪到的人永遠都在圖上。

顏色不是用來區分18個人（18種顏色沒有人分得出來），而是拿他的次數跟**公平範圍**比：深藍「明顯偏少」→ 淺藍「略少」→ 灰「接近平均」→ 橘「略多」→ 深橘紅「明顯偏多」。**整張圖越接近灰色、長度越整齊，就代表這項勤務分配得越平均。**

「公平範圍」是總人次除以應分擔人數的整數區間。例如擦桌子一天只有3個名額，5天下來15人次要分給16個人，那每人拿 0 次或 1 次都算公平，拿到 2 次才算偏多——用區間而不是「跟平均值的比例」，才不會在勤務還沒輪完一圈時把所有做過的人都誤判成偏多。固定送便當的兩位不會被排到洗碗、雜項勤務與撤收，計算時會排除，免得他們的 0 次被當成偏少；洗衣籃則是全員一起輪，不排除。打菜、蓋便當、包餐盒這三張圖只算「沒有打菜固定角色」的人，因為打飯、計數、抬飲料的六位本來就不進這個輪替。

配色是 diverging（雙向）色階，已用色盲模擬驗證過相鄰色差（CVD ΔE 17.9、一般視覺 ΔE 18.1，皆通過門檻）。每張圖旁邊都有完整的次數/佔比表格，滑鼠移到扇形上也會顯示明細，不會只靠顏色傳達資訊。

## 雲端同步（選用）

預設資料只存在瀏覽器的 localStorage，清快取或換手機就會不見。「☁️ 雲端同步」分頁可以接上**你自己的 Firebase 專案**，把資料自動備份到雲端，換裝置時填一樣的房間代碼就能整份拉回來，手機和電腦也能看同一份。

設定步驟（分頁裡也有同一份說明和可複製的規則）：

1. 到 [Firebase 主控台](https://console.firebase.google.com/) 免費建一個專案。
2. 新增一個「網頁應用程式」，把它給的 `firebaseConfig` 整段貼進設定框（支援直接貼 `const firebaseConfig = {...};`）。
3. **Build → Firestore Database** 建立資料庫。
4. **Build → Authentication → Sign-in method** 啟用**匿名**登入。
5. 把 Firestore 規則換成：

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /rosters/{roomId} {
      allow read, write: if request.auth != null;
    }
  }
}
```

運作方式：localStorage 仍是主要儲存（離線照常可用），雲端只是鏡像；有變更就延遲 1.5 秒自動上傳，其他裝置透過 `onSnapshot` 即時收到。整份狀態以 JSON 字串存在 `rosters/{房間代碼}` 的單一欄位裡（Firestore 不支援巢狀陣列，直接存物件會有相容性問題）。衝突以最後寫入者為準，畫面會顯示雲端最後更新時間讓你判斷該上傳還是下載。Firebase 設定與房間代碼存在另一個 localStorage key，不會被同步覆蓋，也不會出現在匯出的備份檔裡。

> ⚠️ **安全性**：上面那組規則的意思是「任何登入過的人都能讀寫任何房間」。因為名冊裡有真實姓名，請用分頁裡的「隨機產生」按鈕產一組不好猜的房間代碼並**當成密碼看待**，不要用 `test` 這種。知道代碼的人就能看到、改到你的班表。

沒設定雲端同步的話 App 一樣能正常使用，只是沒有雲端備份；頁腳的「匯出備份／匯入備份」隨時可以另外存一份 JSON 檔。

## LINE 機器人（選用）

把機器人邀進打飯班群組，打一句 **`今日勤務`** 或 **`8/5 勤務`**，它就會回一組**可以左右滑的 9 張卡片**：三餐勤務各一張、261 梯個人分工兩張（01-08／09-13）、263 梯兩張（01-05／06-10）、全日勤務一張，最後一張是公平性總覽（圖片＋「看完整」按鈕，點進去看完整的公平性頁面）。

- 卡片內容跟「文字班表」分頁完全同源（`js/textFormat.js`），不會兩邊長歪。
- 機器人跟網頁跑**同一份排班程式碼**：`api/_lib/app.js` 把 `js/` 底下的腳本丟進 Node 的 `vm` sandbox 執行，只補一個記憶體版的 `localStorage`。規則改一次，兩邊一起變。
- 資料來源是 App「雲端同步」上傳的那份 Firestore，所以在 App 按完「確定紀錄」，機器人下一次回答就是最新的。
- 那天還沒按「確定紀錄」也問得到——機器人會即時算一份預覽，並註明「尚未確定」（排班是決定性的，之後確定會一模一樣）。
- 群組裡沒有出現「勤務」或「班表」就不會回話，不會洗版。

跑在 Vercel 免費方案。完整設定步驟（LINE channel、Vercel 環境變數、LIFF）看 **[docs/LINE-BOT-SETUP.md](docs/LINE-BOT-SETUP.md)**。

「看完整」有兩種接法：設了 `LIFF_ID` 就開 LIFF（要另外建一個 LINE Login channel，因為 LINE 已經不允許把 LIFF 掛在 Messaging API channel 上）；沒設就退回用 `?k=<STATE_READ_KEY>` 開一般網頁，畫面一樣，只是那串 key 會出現在網址上。

不想部署就先看看長怎樣：

```bash
node scripts/bot-demo.js 2026-08-04 ./out      # 印出 9 張卡片的內容 ＋ 存出公平性 PNG
MOCK_ROSTER=1 STATE_READ_KEY=devkey node scripts/dev-server.js 8123   # 本機模擬 Vercel
```

## 改規則之前先跑這個

`scripts/audit-rules.js` 把上面每一條規則都寫成斷言，對 8/1～8/14 全部跑一遍（洗碗不重複、撤收每人每天剛好一次且不跟洗碗撞、抬便當名單、打菜流程人數、退伍／退出／加入日期、採買、洗衣籃銜接、個人分工文字跟班表一致…）。規則互相牽制得很緊，改一條很容易踩到另一條，所以動演算法之前後都跑一次：

```bash
node scripts/dev-server.js 8123 &
BASE=http://127.0.0.1:8123 node scripts/audit-rules.js
```

## 使用方式

直接用瀏覽器開啟 `index.html`，或用任何靜態網頁伺服器（例如 `npx serve .` / `python3 -m http.server`）啟動後瀏覽。頁腳有「匯出備份／匯入備份」可用 JSON 檔備份或轉移資料。
